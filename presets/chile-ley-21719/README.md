# Chile — Ley 21.719

A profile set that finds Chilean personal data in a database and masks it, built for
[Ley 21.719](https://www.bcn.cl/leychile/navegar?idNorma=1209272) on the protection of personal
data. The law does not apply to anonymized data, so the goal is a non-production copy that no
longer identifies anyone: not only the direct identifiers, but also the quasi-identifiers that
re-identify people in combination, and the sensitive categories of article 2 letter g.

The law takes effect on 1 December 2026. A bill sent to the Senate on 31 August 2026
(Boletín 18.623-07) would move that to 1 December 2027; it changes the date, not this set.

## Detection

Every domain has a **Path** classifier on the column name, in Spanish, in the abbreviations of
Chilean legacy systems (`FEC_NAC`, `APE_PAT`, `RUTCLI`, `NRO_CTA_CTE`) and in English. Names that
are ambiguous on their own (`NOMBRE`, `FICHA`, `RESULTADO`, `CIUDAD`) carry a lower strength and
need the values to agree; generic ones exclude what they are not (`NOMBRE_PRODUCTO`,
`CLAVE_PRODUCTO`, `CARGO_FIJO`, `DIRECCION_IP`).

Where the values have a recognizable shape or vocabulary, a **Regex** or **List** classifier finds
the data in columns whose name says nothing (`CAMPO1`, `OBS`, `TEXTO_LIBRE`): RUT, names and
surnames, e-mail, Chilean phone numbers, addresses, cards (Luhn), IPs, MAC and IMEI, plates, VIN,
comunas, indigenous peoples, CIE-10 codes, medicines, blood groups, religions, parties, health
insurers, pension funds, social benefits, court case numbers.

**Type** classifiers rule domains out where the column cannot hold the data: a full RUT is text
of at least 7 characters, a check digit at most 2, a birth date a date, timestamp or text.

## Masking

All algorithms are deterministic for the engine's key, so the same value masks the same way in
every table and every job. Placeholders such as `S/I` or `-` do not fail a row: where there is
nothing to mask they pass through, and text in a RUT or phone column that does not have the
expected shape is masked character by character instead of being left as it was.

### L1 — Direct identifiers

| Domain | Masking |
|---|---|
| `CL_L1_RUT` | Masked body, **valid check digit including K**, same format (see below) |
| `CL_L1_RUT_CUERPO` | The same digit mapping as the body of a full RUT |
| `CL_L1_RUT_DV` | A random check digit — see Limits |
| `CL_L1_NOMBRE`, `CL_L1_APELLIDO` | Word by word from Chilean given-name and surname lists |
| `CL_L1_NOMBRE_COMPLETO` | Given names and both surnames, in Chilean order; `APELLIDOS, NOMBRES` too |
| `CL_L1_EMAIL` | Name and domain mapped character by character, top-level domain `.test` |
| `CL_L1_TELEFONO` | Subscriber digits masked; `+56`, the mobile `9` and area codes kept |
| `CL_L1_DIRECCION` | A fictitious Chilean street address |
| `CL_L1_TARJETA` | Payment Card (Luhn stays valid) |
| `CL_L1_IP` | Each IPv4 octet mapped to 1–254 |
| `CL_L1_PATENTE` | Consonants to consonants, digits to digits: still a valid plate |
| `CL_L1_GEOLOCALIZACION` | Integer part and first decimal kept (about 11 km), the rest masked |
| `CL_L1_TEXTO_LIBRE` | Free Text Redaction: RUT, e-mail, phones, plates, cards, IPs, names |
| `CL_L1_CREDENCIAL` | Every character becomes `X` |
| document, passport, foreign ID, bank account, device, VIN, contract, user and apartment domains | Character Mapping over digits, hex letters, other letters and accented letters separately |

### L2 — Quasi-identifiers

| Domain | Masking |
|---|---|
| `CL_L2_FECHA_NACIMIENTO` | Shifted up to 60 days |
| `CL_L2_FECHA_EVENTO` | Death, hiring, admission and similar dates, shifted up to 30 days |
| `CL_L2_ANIO_NACIMIENTO` | The decade stays, the last digit is masked |
| `CL_L2_EDAD` | The decade stays (37 → 3x); 100 and over becomes 90 |
| `CL_L2_COMUNA`, `CL_L2_CODIGO_COMUNA` | Comunas under 20,000 inhabitants (Censo 2024) become the largest comuna of their province, or of their region when that one is small too |
| `CL_L2_CODIGO_POSTAL` | The comuna part stays, the block part becomes `0000` |
| `CL_L2_SEXO` | Replaced within its own vocabulary (F/M, H/M, Femenino/Masculino, Mujer/Hombre) |
| `CL_L2_CARGAS_FAMILIARES` | Capped at 5 |
| nationality, marital status, occupation, employer, education level, school | Replaced from a list |

### L3 — Sensitive data (art. 2 g)

The categories of the law: ethnic origin, health and human biological profile, biometrics,
sexual life, orientation and gender identity, religious and ideological convictions, political,
union and professional affiliation, **socioeconomic situation** — a category of Chilean law that
GDPR-based templates do not have — and criminal records.

Categorical columns keep their shape: a yes/no flag stays a flag in the same vocabulary, a numeric
code gets other digits, and any other value is replaced from a list of the category (indigenous
peoples, religions, parties, FONASA tiers and ISAPREs, AFPs, RSH tiers, social benefits, housing
tenure, student aid, credit status). Where the values share no vocabulary — reproductive and
mental health, sexual life, union and professional affiliation — they are suppressed to
`Sin información`. Amounts (income, debt, pension balance) are mapped into a plausible range;
CIE-10 codes are replaced by common codes, in the same format.

## The RUT check digit

The RUT check digit is modulo 11 with weights 2 to 7 from the right, and a result of 10 is
written `K`. The plugin's Check Digit framework writes 10 as `0`, so masking a RUT with it alone
leaves about one in eleven results invalid. `CL_RUT` takes two passes:

1. mask the body and write, in the check digit's place, an auxiliary digit computed with every
   weight doubled modulo 11 — that digit is `9` exactly when the real check digit is `K`;
2. where the auxiliary digit is `9`, write `K`; otherwise recompute the real check digit without
   touching the body.

Every masked RUT is valid, `K` appears in its natural proportion, and the mapping stays
one-to-one, so a RUT used as a key cannot collide. Bodies of 6, 7 and 8 digits, with or without
dots and hyphen, upper- or lower-case `k`, keep their format.

## Limits

- **Binary columns** (scanned ID cards, fingerprints, clinical PDFs in BLOBs) cannot be masked by
  these algorithms. The biometric domain only accepts text columns; inventory the binary ones and
  report them as residual risk.
- **RUT split in two columns**: the body masks exactly like the body of a full RUT, but the check
  digit column cannot see the body, so the pair is no longer valid. Mask the concatenated value
  where the application validates it.
- **Data Cleansing leaves unknown values as they are**: a comuna spelled in a way that is not in
  the list (with or without accents and ñ both are) passes unchanged.
- **Free text** is redacted token by token: a phone written with spaces (`+56 9 8765 4321`) is not
  found there, and a given name that is also a common word (`Rosa`, `Paz`) is redacted wherever it
  appears.
- **Minors**: a birth date moves at most 60 days, so few people cross their 18th birthday — but
  some do. Where that matters, split the rule by age group with Multi-Column Condition.
- **Addresses** are replaced as a whole line. Street, number and comuna kept in separate columns
  are masked independently; Multi-Column Address, which keeps them coherent, needs an address
  file of its own.

## Checking

```bash
node presets/chile-ley-21719/build.mjs
node presets/chile-ley-21719/verify.mjs
node presets/_doc/build.mjs chile-ley-21719
```

The last one regenerates the PDFs; run it after any change to the set or to `doc/`.

`verify.mjs` reviews every classifier configuration, profiles 129 columns with the whole set at
its threshold — well named, badly named and 21 columns that are not personal data — and masks
184 sample values and 204 placeholders through the running app (`DLPX_URL`, default
`http://localhost:3000`), including 60 random RUTs checked for a valid check digit.
